# AGENTS.md — Правила работы агентов в проекте

> Этот файл обязателен к прочтению для любого агента (человека или ИИ), работающего над этим репозиторием.
> Правила действуют в порядке убывания приоритета: **Безопасность > Корректность > Минимальность кода > Скорость**.

---

## 1. Обязательный рабочий цикл (Spec-Driven Development)

Каждая нетривиальная задача проходит строго по этапам. Пропуск этапа — нарушение.

```
Спецификация (spec.md)
       ↓
     План (plan.md)
       ↓
   Задачи (tasks.md)
       ↓
      Код
       ↓
   Тест / Проверка
```

### Этап 0 — Спецификация (`spec.md`)

- Создаётся по шаблону `.specify/templates/spec-template.md`.
- Содержит: пользовательские истории (P1/P2/P3), функциональные требования (FR-XXX), критерии успеха (SC-XXX), допущения.
- **Не приступай к плану, пока spec не одобрена.**

### Этап 1 — План (`plan.md`)

- Создаётся по шаблону `.specify/templates/plan-template.md`.
- Определяет: технический контекст, структуру файлов, зависимости, ограничения.
- Проверяет соответствие `constitution.md` (раздел "Constitution Check").

### Этап 2 — Задачи (`tasks.md`)

- Создаётся по шаблону `.specify/templates/tasks-template.md`.
- Каждая задача: атомарная, проверяемая, с чётким критерием завершения.
- Статусы: `[ ]` → `[~]` (в работе) → `[x]` (готово).

### Этап 3 — Код

- Пишется только после утверждённых tasks.md.
- Применяются все принципы раздела 2.

## 2. Принцип минимального кода (Ponytail / Lazy Senior Dev)

> **Лучший код — тот, который не написан.**

### Перед тем как писать

1. **Изучи задачу и затронутый код** — перечисли все места: вызывающие функции, тесты, фикстуры, конфиги, экспорты.
2. **Проверь последствия** — что сломается у пользователей, какие данные могут быть уничтожены или раскрыты.
3. Это и есть область действия. Ничего сверх этого.

### Алгоритм выбора решения (первое подходящее побеждает)

| # | Вопрос | Действие |
|---|--------|----------|
| 1 | Это вообще нужно? | Отбросить. Указать в одной строке. |
| 2 | Уже есть в кодовой базе? | Использовать, как окружающий код. |
| 3 | Стандартная библиотека или платформа? | Использовать её. |
| 4 | Установленная зависимость? | Использовать. Никогда не добавлять зависимость ради пары строк. |
| 5 | Однострочник, понятный без объяснений? | Написать его. |
| 6 | Иначе | Минимальный рабочий код. |

### Запрещено

- Абстракции, обёртки, опции и конфигурации, которых никто не запрашивал.
- Код «на будущее» без явного требования.
- Добавление новой зависимости ради нескольких строк.
- Преобразования типов, если платформа уже даёт нужное значение.

### Обязательно

- **Завершить каждую часть задачи**: вызывающие функции, тесты, фикстуры.
- Побеждает **кратчайший рабочий diff**, при условии что он затрагивает всё нужное.
- Удаление лучше добавления. Структура кодовой базы сохраняется.
- Если сокращение имеет известный предел — добавь комментарий: `# shortcut: <limit>, <when to upgrade>`.

## 3. Безопасность, валидация и изоляция логики

Эти правила **не имеют исключений** — даже ради краткости кода.

### Безопасность

- **Всегда** проверяй входные данные на границах доверия (HTTP, CLI, файлы, БД).
- Никакого раскрытия внутренних ошибок наружу (трейсбеки, пути ФС, секреты).
- Используй параметризованные запросы — никогда не интерполируй SQL вручную.
- Секреты только через переменные среды или `.env.local` (не в коде).

### Валидация

- Валидируй **на входе**, не на выходе.
- Возвращай понятные ошибки пользователю, детали — только в логи.
- Обработка ошибок при перемещении/объединении кода **сохраняется** — не выбрасывай её.

### Изоляция логики

- Бизнес-логика не зависит от фреймворка напрямую — её можно протестировать без HTTP-запроса.
- Одна функция / класс — одна ответственность.
- Новая нетривиальная логика (ветвление, цикл, парсер, деньги, безопасность) **требует хотя бы одного теста**.

## 4. GSD — Пошаговое выполнение (Get Shit Done)

- **Одна задача за раз** из `tasks.md`. Не переходи к следующей до завершения текущей.
- Задача завершена = код написан + тест проходит + статус обновлён в `tasks.md`.
- Если задача оказывается больше, чем ожидалось — разбей её на подзадачи **до** начала кода.
- Промежуточные результаты коммитятся с понятным сообщением.
- После завершения всех задач — финальная проверка по критериям успеха из `spec.md`.

## 5. Структура папки `.specify`

Папка `my-project/.specify/` содержит инфраструктуру воркфлоу:

```
my-project/.specify/
├── templates/
│   ├── spec-template.md        ← шаблон спецификации
│   ├── plan-template.md        ← шаблон плана
│   ├── tasks-template.md       ← шаблон задач
│   ├── checklist-template.md   ← чеклист проверки
│   └── constitution-template.md
├── memory/
│   └── constitution.md         ← правила проекта (Constitution Check)
├── scripts/python/             ← скрипты создания фич (speckit)
└── workflows/                  ← workflow-registry для автоматизации
```

**Для новой фичи** используй скрипт:
```bash
cd my-project
python .specify/scripts/python/create_new_feature.py "Название фичи"
```

## 6. Краткая памятка агента

```
ДО КОДА:
  ✓ spec.md создан и одобрен
  ✓ plan.md написан по шаблону
  ✓ tasks.md содержит атомарные задачи

ПРИ НАПИСАНИИ КОДА:
  ✓ Минимальный diff, покрывающий всё нужное
  ✓ Нет абстракций без запроса
  ✓ Входные данные валидируются
  ✓ Секреты — только из env
  ✓ Нетривиальная логика — с тестом

ПОСЛЕ КОДА:
  ✓ tasks.md обновлён ([x])
  ✓ Тесты проходят
  ✓ Критерии успеха из spec.md выполнены
```
